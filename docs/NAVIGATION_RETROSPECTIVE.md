# Defense3 寻路修改复盘

截至 2026-09-12，这次寻路工作的主线合理：从局部绕障走向共享计算，再补齐动态地图、碰撞和持续追击，符合大量敌人追踪目标的需求。但多类问题被连续当作“寻路问题”处理，行为规则、实际物理契约、状态稳定性和验收没有及早一起明确。返工有多个来源，不能简单归咎于“你选错算法”或“提示词不够好”；实现遗漏、验证范围不足和代理处理流程，也需要承担相应解释。

本文依据 Git、计划、执行报告、OpenSpec 与 `bugs.md` 整理，没有读取完整历史聊天，也没有重新运行游戏或测试。日期优先采用记录日期；若多个修复交错，按问题依赖叙述，不把计划排列当作精确施工时间线。下文“记录”指仓库已有证据，“判断”指基于证据的分析。无法据此精确统计工时、返工比例或个人责任；现存规格也可能已被后续需求修改，不能反推早期实现应该遵守最终规则。

9/5 的 Git `2fe1561`、`712b82a` 可以确认空气墙和 Boss steering 的演进；可核实的 PathAgent A* 到9/8才出现。9/8的 `db92096` 提交名只是“保存”，里面已经是止损后的参数，所以不能仅靠提交标题还原每次尝试；报告与 bugs 保留了中间过程。[前期问题记录](C:/Users/Admin/Defense3/bugs.md:516)

这里最关键的概念是：**共享实现不等于共享计算。** 把 A* 写进同一个类，提高了代码一致性，但200只怪各自调用，仍然可能进行200份搜索。低频重算也只是降低平均频率，不能自动避免很多单位同一帧一起重算。对于大量同目标小怪，共享流场很合理；对于数量少、目标不同的单位，A* 本身并没有错。真正应先比较的是单位数、目标数、地图规模、重建频次和帧预算。

早期 PathAgent 的机器验收主要检查 TypeScript、调用接线以及“没有每帧无条件重算”；报告明确没有跑实玩。这些检查能证明代码接上了，不能证明大量单位不卡，也不能证明复杂障碍能绕开。流场阶段逐步改为加载真实角色类、测试共享次数和状态边界，是验证质量的进步。[初期性能验收](C:/Users/Admin/Defense3/.cursor/plans/shared-path-agent.md:103)

**二、流场之后，瓶颈从重复计算变成冷启动，再变成完成延迟**

9/9性能调查把两个用户现象分开：滚木接触时约55降到25 FPS；建造时降到5–10 FPS。代码和核心反例确认，受阻起点仍会枚举288个外围候选，每个候选再触发目标场，最多建立289份。服务还在稳定帧扫描全场、排序和构造签名；多条建造通知让没有变化的地图也反复失效。此时继续调粗格子或减少怪物，并不能解决重复工作的来源。

修复把完整直通判断放在建场之前，阻挡起点立即安全返回；候选可达性使用共享连通图；缓存设定上限；通知先置脏，再按真实变化提交；体型改用稳定的物理几何，最终速度重新接受碰撞约束。这一轮已经形成“反例—计数—修复—同输入对比”的有效闭环。

| 实际35717格地图的 Node 核心样本 | 修前中位数 | 修后中位数 |
|---|---:|---:|
| 200次无遮挡查询 | 32.572ms | 4.840ms |
| 单次无解冷查询 | 3595.904ms | 290.820ms |
| 滚木重叠冷查询 | 6018.033ms | 约0.0019ms，零图、零BFS |
| 无解热查询200次 | 206.010ms | 8.194ms |
| 移动体型和目标200次 | 3293.052ms | 9.819ms |

这些是同机、实际TS代码、五轮样本的核心基准，不能换算为游戏FPS。极小耗时的可信结论是“零搜索”，不是小数点后的精度。稳定300帧的全场扫描从300次降到1次；五次无变化通知的版本递增从5次降到0次。与此同时，单次冷建图仍约291ms，报告已经明确保留卡顿风险；预览当时加载中间旧编译块，最终补丁没有可比的真实FPS证据。[完整性能报告](C:/Users/Admin/Defense3/.cursor/plans/reports/fix-enemy-navigation-performance-report.md:39)

随后 `fix-enemy-navigation-rebuild-stalls` 把冷任务分帧。已有trace显示一次回调约166ms，其中graph约154ms，证明热点落在建图。v1限制为256 work/frame，虽然切小了单帧工作，但graph需要489帧，field需要241帧：单位长时间等不到结果。v2增加到4096 work/frame，p95达到24.4904ms，超过该轮8ms验收线，失败。v3减少冗余前置graph并优化邻边检查，field约35帧、graph约39帧，Node切片p95为6.0898ms、最大11.144ms。

这不是“分帧方向错了”。它说明必须同时约束**单帧成本和从请求到可用的延迟**：预算太小可能不掉帧却长时间不动；只增预算又会重新卡顿。降低每单位工作的成本，才使两端同时改善。这里也不能写整份计划全部完成：v1–v3产物保留，v4入口pending修复没有完成，后来被统一导航方案取代。[分帧报告](C:/Users/Admin/Defense3/.cursor/plans/reports/fix-enemy-navigation-rebuild-stalls-report.md:62)

**三、后续难点已经超过“选一种更快的算法”**

| 问题层 | 仓库记录的现象、原因与修改 | 对复盘的意义 |
|---|---|---|
| 地图规则 | 早期按城内外、三条楼梯和开闭状态通行；后来 `enemy-unified-navigation` 取消区域/portal限制，按实际几何及 Ignore、Hard、Destructible分类，同时修复连通标签过早递增 | 入口机制当时符合规格；后来取消是需求简化，不能用最终规则判定用户早期“做错了” |
| 拆障决策 | 最初物理可绕就绕、完全无路才拆；后来改为Hard-only规划，选中路线遇到合格可拆物就拆，即使物理上存在绕路 | “能绕就绕”与“挡路就拆”是玩法差异，优化同一个BFS不能自动决定正确答案 |
| 物理契约 | 导航漏采多边形；世界速度直接写入Box2D，比例32没有统一；目标自身碰撞否决移动/攻击；断开连通区缺少边界接近点 | 抽象地图可达，不保证真实角色能移动到攻击位置；导航与实际碰撞必须使用一致的体型、单位和终点语义 |
| 失效传播 | 静态刚体连续发同值transform通知，旧任务每帧被取消；改为事件仅置脏，下一次快照确认实际变化才失效 | 收到通知不等于地图改变；要区分请求次数、真实提交次数和取消原因 |
| 生命周期与状态 | 建筑与导航循环导入造成Tower基类undefined/MissingScript，改为事件解耦；目标重选、攻击、死亡和池复用也会重置路线或旧回调 | 模块依赖与对象状态错误，可以让正确的搜索核心完全发挥不了作用 |

**四、你的方向是否错误，时间主要花在哪里**

我的判断是：你持续指出真实游戏里的不动、掉帧、绕而不拆、反复走动，并提供trace/debug与具体复现，推动问题从“代码看起来合理”走向真实行为，这是必要反馈。去除额外区域规则、澄清只拆所选路线上的合格障碍，也帮助缩小了问题。流场、分帧、实际碰撞统一都属于合理演进；其中确有临时止损和后续替代，但不等于所有前期工作白做。几何安全、共享缓存、计数、状态回归都被后续保留下来。

可避免的弯路主要是先扩算法再补契约：规模预算晚于四类单位全面接入，候选失败路径晚于共享逻辑，物理单位和攻击终段晚于抽象可达，路线承诺晚于拆障决策。若更早锁定这些边界，可以少做一部分重构；这需要代理主动识别和验证，不应要求用户预先懂所有技术细节。

耗时应分成四类看：动态几何、体型、对象池与拥挤处理属于必要技术工作；重复BFS、假失效、比例不一致、状态反复reset属于可避免实现遗漏；取消入口约束、调整绕行与拆除优先级属于真实需求变化；重新survey、文档权限遗漏、报告不同步则是流程开销。Boss retained v1仅因计划自身未列入可写就在写前硬阻塞，v2再补，是后一类实例。没有完整聊天和工时记录，不能给各类编造百分比。

更优质的对话不是一次写一篇更长的提示词，而是尽早固定关键分歧，每轮保留可重复证据，把“改了代码”“机器通过”“真实玩法通过”分别记录。

**五、可以直接复制的提示词**

下面模板来自本仓库复盘，并非已核实的官方建议。方括号替换成当前情况；不确定项允许代理先读代码、场景和报告确认。

**A．新任务：先固定行为和规模。**

> 目标是让[哪些单位]在[真实关卡]中稳定到达并攻击目标。请先读取相关规格、bugs和现有实现，列出已确认事实、影响方案的未知项及最小实现范围。先整理行为表：Hard如何绕行，可拆物何时绕/拆，目标移动、无路、攻击、死亡/复活时如何处理。重要行为分歧优先澄清，不让我先选算法。
>
> 规模是[常态/峰值单位数]、[主要目标数]、[实际地图范围]；性能要求同时包含每帧导航成本和请求到路线可用的延迟。不要把共享代码当成共享计算，也不要自行降低碰撞精度、怪数或改变玩法换性能。用少量单位完成真实场景出生→绕障/拆障→实际扣血的小闭环，同时建立轻量性能基线并核算200单位或约定峰值的预算，再扩大真实压力验证；不要等全部功能完成才测性能。提出验证方法，未知阈值标为待定。

**B．报bug：提供现象，让日志证伪猜测。**

> 现象：[具体看到什么]。最短复现：[出生位置、建造/滚木状态、目标位置与操作顺序]。预期：[应该发生什么]。我的猜测是[可空]，请不要直接当作原因。先提出最多三个最可能假设，用现有日志或最小诊断逐项证伪；确认原因后做最小修复。
>
> 先确认运行bundle与磁盘源码版本/hash一致。按故障相关性采样：位置、body/offset、collider快照和障碍版本；pending/build/cancel/reset次数与原因；当前目标、路点、承诺；规划速度、避让后速度、碰撞约束后速度、刚体速度、真实位移和伤害。给出证据对应的结论，区分“没路”“还没算完”“状态被重置”“物理不允许”“到了却打不到”。诊断按需聚合，不制造逐帧日志洪水。
>
> 先用能证明本次故障的回归确认修前失败、修后通过，再跑相关集成。若是需求与规格不一致，明确指出分歧后调整，不通过放松测试或改攻击范围掩盖问题。

当前项目已有 `EnemyNavDebug.start/list/select(uuid)/stop/export/download`。优先复用现有15秒/900帧诊断，只补缺失的运行版本或完整几何信息，避免再造一套采集器。具体入口见 [EnemyMinion.ts](C:/Users/Admin/Defense3/assets/scripts/enemy/EnemyMinion.ts:699)。

**C．续跑：保留已完成工作，修失败点。**

> 继续[slug]，从计划和报告的首个未完成步骤续跑。读取当前git/disk状态及相关变化，保留已完成产物和已通过AC，只修改失败步骤与相关AC，不另开build从头survey。
>
> 没有实质扩大范围时，可自主修正计划状态、文件清单等元数据，补齐保持断言语义的测试mock；不得借此修改玩法或削弱验证。真正的业务歧义、破坏性操作或授权范围变化再说明原因。交付写清本次改动、失败如何被证伪、哪些检查通过、真实场景还缺什么；不要重复所有无关测试，也不要把机器done写成实玩通过。

实际验收建议保留六组短场景，并固定输入以便对比：无遮挡追移动目标；薄墙/窄通道与两种体型；固定木挡住selected route并实际扣血；建造改变通路且中途目标移动；无路后移除障碍并恢复；攻击、死亡、池复用与峰值拥挤。每组同时观察安全性、进展性、帧成本和ready延迟。安全性包括不穿墙、不隔墙伤害；进展性包括有路会接近、有资格会出手、环境恢复后会继续，不只检查返回速度非零。

阈值应先由目标设备与帧预算确定。例如“导航切片p95≤4ms、最大≤8ms，普通路线请求≤0.5秒可用，有效通路下连续1秒无进展触发诊断”只能作为商议起点，不是本次已达成成绩，也不适合所有地图。采用小规模真实闭环、峰值压力样本和必要回归后，只有新失败、新改动或未解决疑点才扩大、重跑测试。最终真实场景通过才称玩法验证完成；脚本任务机器done可以单独保留，避免把缺失的体验证据隐藏在一个“通过”里。
